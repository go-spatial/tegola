# Contributing to this fork

Thanks for your interest in contributing! This repository is a fork of
[go-spatial/tegola](https://github.com/go-spatial/tegola) maintained by
[@alexeydott](https://github.com/alexeydott). The fork adds, among other
things, the unified CRS contract (`srid` / `crs_defn`, synthetic SRIDs),
shared geometry formats (`wkb`/`wkt`/`mos` via `provider/geometrycodec`),
the reworked GeoPackage provider, MySQL and HANA MVT support, OGC feature publication, conditional mutations and WFS transactions.
See [CHANGELOG.md](CHANGELOG.md) for the fork-specific history.

## Where to report things

* Bugs and feature requests: open an issue in **this** repository
  (`alexeydott/tegola`), not upstream.
* Security-sensitive reports: see [SECURITY.md](SECURITY.md) - please do not
  open a public issue for them.
* Upstream bugs (things that reproduce on `go-spatial/tegola` too) are best
  reported upstream; link the upstream issue from a fork issue if the fork
  is also affected.

## Building from source

This project uses Go modules (no GOPATH setup, no `go get`-based installs)
and vendors its dependencies.

```bash
git clone https://github.com/alexeydott/tegola.git
cd tegola
go build -mod vendor ./cmd/tegola
```

The GeoPackage provider uses CGO (sqlite3). To build without CGO
(`CGO_ENABLED=0`) the gpkg provider is excluded automatically via its build
tag. To regenerate any autogenerated assets run:

```bash
go generate ./...
```

## Running the tests

Run the full suite with CGO enabled (this covers the gpkg provider):

```bash
go test ./...
```

and again without CGO:

```bash
CGO_ENABLED=0 go test ./...
```

Integration tests only run when the corresponding environment variables are
set to `yes`:

* `RUN_POSTGIS_TESTS=yes` with `PGURI` (e.g. a PostGIS URI);
  `PGURI_NO_ACCESS` optionally exercises permission errors
* `RUN_MYSQL_TESTS=yes`; the live construction test in `provider/mysql`
  connects to `localhost:3306`, database `test`, user `u`, password `p` -
  the same credentials the `mysql` service in `docker-compose.yml` creates
* `RUN_HANA_TESTS=yes` with `HANA_CONNECTION_STRING` (a SAP HANA DSN,
  usually provided as a CI secret)

The easiest way to get a PostGIS instance for the integration tests is the
compose file in the repository:

```bash
docker compose up -d --wait redis postgis mysql
docker compose run --rm migration
```

Set the native test environment variables only for the disposable services above. Mutation suites have separate opt-in DSNs described in [provider evidence](docs/provider-matrix.md).

## Dependencies and `third_party/`

Dependencies are vendored. To change a dependency:

1. edit `go.mod` (`go get dependency@version`),
2. run `go mod tidy && go mod vendor`,
3. commit the updated `go.mod`, `go.sum` and `vendor/` together with your
   change.

The low-level `geom` and `proj` modules are published forks under
`github.com/alexeydott/`; there are no dependency replacements. Patch their
standalone repositories, test and tag a new version, then update Tegola
requirements and regenerate vendor. The old `third_party/go-spatial` trees
are frozen audit snapshots, not active sources. `maths/makevalid` is Tegola
code. See [dependency ownership and migration](third_party/README.md).

## Branches and pull requests

* The default branch is the fork's integration branch; feature work happens
  on feature branches (`fix/<topic>`, `feat/<topic>`).
* Base your pull request on the default branch and keep it focused; one
  logical change per PR.
* Reference the relevant issue when one exists; stage intended files explicitly.

## Conventions

* Format code with `go fmt ./...`. If formatting changes touch code you
  are not working on, submit them as a separate PR.
* Do not add `Co-authored-by` trailers to commit messages.
* Error variables are declared as `var ErrSomething = errors.New("provider: message")`
  - lowercase text, no trailing punctuation.
* New provider config keys must be documented in the provider README and,
  where they are part of the shared contract, in
  [docs/provider-contract.md](docs/provider-contract.md).
  `atlas/provider_docs_sync_test.go` enforces part of this.

## Testing expectations

* New behaviour needs tests. Unit tests must run without a database; use
  sqlmock or in-memory sqlite where appropriate.
* Both CGO and non-CGO builds must pass locally. The workflow defines the
  same matrix; record actual remote CI results separately from local verification.
* Run `go vet ./...` and keep the non-test code clean.

## Documentation

Keep published Markdown about product behavior, configuration, architecture,
compatibility and contributor guidance. Do not include internal implementation
plans, audit-pass names, task/role codes or agent execution records. Preserve
useful findings as verified contracts and limitations. Historical release notes
must not imply that an older tag includes later source changes.
